# 📘 RelayChat — Developer Project Guide

> This guide is written for **you, the original developer**, so that when you revisit this project months later, you can understand everything quickly — the architecture, every module, every flow, and every design decision.

---

## 1. Project Purpose

**RelayChat** is a real-time, one-to-one chat application. Its core goals are:

1. Allow users to log in using **just their email** (OTP-based, no password)
2. Chat in **real time** with other registered users
3. Send **text and image messages**
4. See **read receipts** and **typing indicators**
5. Know which users are **online**

It was built as a **learning project** to explore **microservices patterns**, **message queues**, **WebSockets**, and modern full-stack TypeScript development.

## 4. How Each Major Module Works

### 4.1 `tryCatch.ts` — Error Wrapper
A Higher-Order Function that wraps any Express `RequestHandler`. If the handler throws, it catches the error and sends `{ message: error.message }` with status 500. **This is used on every single controller function** in both backend services.

```ts
const TryCatch = (handler) => async (req, res, next) => {
    try { await handler(req, res, next) }
    catch (error) { res.status(500).json({ message: error.message }) }
}
```

### 4.2 `isAuth` Middleware (both services)
- Reads `Authorization: Bearer <token>` header
- Verifies JWT using `JWT_SECRET`
- Attaches decoded `user` to `req.user`
- Responds 401 if missing/invalid
- Note: Both user service and chat service have **their own copy** of this middleware — they are not shared

### 4.3 `rabbitmq.ts` (User Service — Publisher)
- Connects to RabbitMQ on startup via `ConnectRabbitmq()`
- Stores the channel in a module-level variable
- `publishToQueue(queueName, message)`: asserts the queue as durable and sends the JSON-encoded message with `persistent: true`

### 4.4 `consumer.ts` (Mail Service — Consumer)
- Connects to RabbitMQ on startup
- Asserts queue `"send-otp"` (must match publisher)
- For each message: parses `{ to, subject, body }` → sends email via Nodemailer + Gmail SMTP → `channel.ack(msg)` to remove from queue

### 4.5 `socket.ts` (Chat Service)
- Creates an `http.Server` wrapping an Express `app` — **this is how Socket.IO works** (it attaches to the raw HTTP server, not Express directly)
- `userSocketMap: Record<string, string>` — maps `userId → socketId`
- On `connection`: maps the user, broadcasts `getOnlineUser`
- On `disconnect`: removes from map, re-broadcasts
- On `joinChat(chatId)`: socket joins that room → used for targeted message delivery
- On `leaveChat(chatId)`: socket leaves room
- On `typing` / `stopTyping`: relays to the chat room

## 7. Authentication Flow

```
1. POST /login { email }
   - Redis rate limit check: otp:ratelimit:{email} (60s TTL)
   - Generate 6-digit OTP
   - Redis set: otp:{email} = OTP (300s = 5 min TTL)
   - Redis set: otp:ratelimit:{email} = "true" (60s TTL)
   - publishToQueue("send-otp", { to, subject, body })
   → 200 OK

2. Mail Service (async)
   - Consumes RabbitMQ message
   - Sends email via Gmail SMTP

3. POST /verify { email, otp }
   - Redis get: otp:{email}
   - Compare stored OTP vs entered OTP
   - If match: Redis del otp:{email}
   - Find or create User in MongoDB
   - generateToken(user) → JWT (15 days)
   → 200 { user, token }

4. Frontend stores token in cookie (js-cookie, 15 days)
   - All subsequent requests: Authorization: Bearer <token>
   - isAuth middleware verifies and attaches req.user

5. Logout: Frontend removes cookie → isAuth = false → redirect to /login
```

**Key design:** There are no passwords stored anywhere. The OTP in Redis is the temporary secret.

## 8. Database Schema

### MongoDB Database: `chatAppMicroservices`

Both user and chat services connect to the **same MongoDB database** (`dbName: "chatAppMicroservices"`).

#### Collection: `users` (User Service)
```
{
  _id: ObjectId,
  name: String (required),      // auto-set to email.slice(0, 8) on first login
  email: String (required, unique),
  createdAt: Date,
  updatedAt: Date
}
```

#### Collection: `chats` (Chat Service)
```
{
  _id: ObjectId,
  users: [String],              // array of 2 user _id strings (not ObjectId refs!)
  latestMessage: {
    text: String,               // preview text or "📷 Image"
    sender: String              // sender's user ID
  },
  createdAt: Date,
  updatedAt: Date
}
```
> ⚠️ **Important:** `users` is an array of plain `String`, not ObjectId refs. This is a design choice — cross-service IDs are stored as strings to avoid coupling.

#### Collection: `messages` (Chat Service)
```
{
  _id: ObjectId,
  chatId: ObjectId (ref: Chat, required),
  sender: String (required),    // user _id as string
  text: String (optional),
  image: {
    url: String,                // Cloudinary URL
    publicId: String            // Cloudinary public ID (for deletion)
  } (optional),
  messageType: "text" | "image" (default: "text"),
  seen: Boolean (default: false),
  seenAt: Date (default: null),
  createdAt: Date,
  updatedAt: Date
}
```

## 9. API Routes — Full Detail

### User Service (Port 5000)

#### `POST /api/v1/login`
- **Body:** `{ email: string }`
- **Logic:** Rate limit check → generate OTP → store in Redis (5 min) → publish to RabbitMQ → 200
- **Auth:** None
- **Errors:** 429 = too many requests

#### `POST /api/v1/verify`
- **Body:** `{ email: string, otp: string }`
- **Logic:** Get OTP from Redis → compare → delete from Redis → find or create user → generate JWT → 200
- **Auth:** None
- **Errors:** 400 = invalid/expired OTP

#### `GET /api/v1/me`
- **Logic:** isAuth middleware resolves user from JWT → return req.user
- **Auth:** ✅ Required

#### `GET /api/v1/user/all`
- **Logic:** `User.find()` — returns all users
- **Auth:** ✅ Required
- **Used by:** Frontend "People" panel to show new chats

#### `GET /api/v1/user/:id`
- **Logic:** `User.findById(id)` — single user lookup
- **Auth:** ❌ Not required
- **Used by:** Chat Service internally via axios

#### `POST /api/v1/update/user`
- **Body:** `{ name: string }`
- **Logic:** Find user → update name → save → regenerate JWT (because user object in token changes) → 200
- **Auth:** ✅ Required

---

### Chat Service (Port 5002)

#### `POST /api/v1/chat/new`
- **Body:** `{ otherUserId: string }`
- **Logic:** Check if chat exists between these 2 users (`$all` + `$size: 2`) → if yes return existing `chatId`, if no create new Chat → 201
- **Auth:** ✅ Required

#### `GET /api/v1/chat/all`
- **Logic:** Find all chats where `users` contains `req.user._id` → for each chat, call User Service via axios to get the other user's name → count unseen messages → sort by updatedAt desc → return
- **Auth:** ✅ Required

#### `POST /api/v1/message`
- **Body:** FormData `{ chatId, text?, image? }`
- **Middleware:** multer → Cloudinary upload
- **Logic:**
  1. Validate user is in chat
  2. Check if receiver's socket is in chatId room → if yes, mark as `seen: true` immediately
  3. Create message document
  4. Update `chat.latestMessage`
  5. Emit `newMessage` to: chatId room, receiver's direct socket, sender's direct socket
  6. If receiver was in room, also emit `messagesSeen` to sender
- **Auth:** ✅ Required

#### `GET /api/v1/message/:chatId`
- **Params:** `chatId`
- **Logic:**
  1. Verify user is in chat
  2. Find all messages where `sender ≠ req.user` and `seen: false` → mark them `seen: true`
  3. Emit `messagesSeen` event to sender's socket (notify sender their messages were read)
  4. Fetch all messages sorted by createdAt asc
  5. Axios call to User Service for the other user's name
  6. Return `{ messages, user }`
- **Auth:** ✅ Required

## 10. Socket / Realtime Logic

### Server-side (`socket.ts`)

```
userSocketMap = { "userId123": "socketId_abc", ... }
```

When a user connects, their `userId` (passed as query param `?userId=xxx`) is mapped to their `socketId`. Each user socket also automatically joins a **personal room** named after their own `userId`:
```ts
socket.join(userId)  // personal room for direct delivery
```

**Events handled:**
| Client emits   | Server action                                                       |
|----------------|---------------------------------------------------------------------|
| `joinChat`     | `socket.join(chatId)` — user enters a chat room                    |
| `leaveChat`    | `socket.leave(chatId)` — user leaves the chat room                 |
| `typing`       | `socket.to(chatId).emit("userTyping", data)` — relay to room       |
| `stopTyping`   | `socket.to(chatId).emit("stopTyping", data)` — relay to room       |
| `disconnect`   | Remove from `userSocketMap`, re-emit `getOnlineUser`               |

**Message delivery strategy** (in `sendMessage`):
1. `io.to(chatId).emit("newMessage", ...)` — anyone in the chat room gets it
2. `io.to(receiverSocketId).emit("newMessage", ...)` — direct to receiver
3. `io.to(senderSocketId).emit("newMessage", ...)` — confirm to sender

The duplication check on the frontend (`currentMessages.some(msg => msg._id === message._id)`) prevents duplicate rendering from multiple emit paths.

### Client-side (`SocketContext.tsx`)

- Connects with `io(chat_service, { query: { userId: user._id } })`
- Listens for `getOnlineUser` → stores in `onlineUsers` state (array of userIds currently connected)
- Disconnects when user logs out (component unmount)

### Client-side (`chat/page.tsx`)

```
socket.on("newMessage")      → if same chat, add to messages; else increment unseenCount in sidebar
socket.on("messagesSeen")    → update seen + seenAt on matching message IDs
socket.on("userTyping")      → setIsTyping(true) in header
socket.on("stopTyping")      → setIsTyping(false) in header
```

## 11. Data Flow: Frontend → Backend → Database → Frontend

### Sending a Message (complete round trip)

```
User types → handleTyping() → emit "typing" to socket

User clicks Send → handleMessageSend()
  → FormData: { chatId, text/image }
  → POST /api/v1/message (with Bearer token)
    → isAuth middleware validates JWT
    → multer middleware: if image file, uploads to Cloudinary → sets req.file.path + req.file.filename
    → sendMessage controller:
        → finds Chat in MongoDB
        → checks if receiver's socket is in chatId room (isReceiverInChatRoom)
        → Creates Messages document in MongoDB
        → Updates Chat.latestMessage in MongoDB
        → io.to(chatId).emit("newMessage", savedMessage)
        → io.to(receiverSocketId).emit("newMessage", savedMessage)
        → io.to(senderSocketId).emit("newMessage", savedMessage)
        → if receiver was in room → io.to(senderSocketId).emit("messagesSeen", ...)
    → res.status(201).json({ message: savedMessage, sender: senderId })
  → Frontend: setMessages(prev => [...prev, data.message])
  → Frontend: moveChatToTop(chatId, { text, sender })

Receiver's browser:
  → socket.on("newMessage") fires
  → if receiver is in same chat → setMessages (add message)
  → else → moveChatToTop with unseenCount+1
```

## 12. Important Design Decisions

### Why Microservices?
This was a deliberate learning choice. The three services (user, chat, mail) can be developed, deployed, and scaled independently. The trade-off is complexity — running 3+ servers locally.

### Why the same MongoDB database?
Both user and chat services connect to the same `chatAppMicroservices` database. This was a practical shortcut — in a production microservice setup each service would have its own database. The current setup means both services share the same MongoDB Atlas cluster.

### Why RabbitMQ for emails (not direct SMTP from user service)?
OTP emails don't need to be synchronous. Using RabbitMQ decouples the user service from the mail server — if mail fails, the queue retries; the user gets a response immediately without waiting for email delivery.

### Why Redis for OTP (not MongoDB)?
OTP values have a natural TTL (5 minutes). Redis supports key expiry natively. Storing temporary data in MongoDB would require manual cleanup jobs.

### Why users stored as String in Chat.users[]?
Cross-service references. The user IDs come from MongoDB ObjectIds (in the user service), but the chat service stores them as plain strings to avoid introducing a foreign key dependency on MongoDB ObjectId types.

### Why JWT is re-issued on name update?
The JWT payload contains the full user object. If the name changes, the old token would return the old name from `/me`. Re-issuing the token keeps the frontend's `req.user` fresh without a separate state sync.

### Typing indicator via Socket (not REST)?
Typing events are ephemeral and high-frequency. Making a REST API call every keystroke would be inefficient. Socket.IO events are the right tool here.

## 15. How to Debug This Project

### Common Issues

**❌ "Redis url not defined"**
→ Check `backend/user/.env` has `REDIS_URL` set

**❌ "failed to connect to rabbit"**
→ RabbitMQ Docker container is not running. Run:
```bash
docker start rabbitmq-container
```

**❌ Messages not appearing in real time**
→ Check that the Chat Service is running (`npm run dev` in `/backend/chat`)
→ Check browser console for socket connection errors
→ Verify `chat_service` URL in `appContext.tsx` matches the running port

**❌ "Please Login - No auth header"**
→ Token is missing from cookie. Try logging in again.
→ Check that cookies are being set properly after `/verify`

**❌ Images failing to upload**
→ Check Cloudinary env vars in `backend/chat/.env`
→ Check file size (limit is 5MB)
→ Check file type (only image/* allowed)

**❌ OTP email not arriving**
→ Check that RabbitMQ is running and consumer started
→ Check mail service logs for `"OTP mail send to..."`
→ Verify Gmail App Password (not regular password) in mail `.env`

### Debug Strategy

1. Start all 4 services and check their console logs
2. All controllers are wrapped in `TryCatch` — errors will appear in terminal
3. Check the RabbitMQ Management UI at `http://localhost:15672` (admin/admin123) to see queue state
4. Use the browser Network tab to inspect HTTP requests + responses
5. Use browser console to see socket events (there are `console.log` statements throughout `chat/page.tsx` and `socket.ts`)

## 16. How to Extend the Project in Future

### Add Group Chats
- Modify `Chat.users[]` to support > 2 users
- Update `createNewChat` to accept an array of `otherUserIds`
- Update `getAllChats` to loop through all other users
- On frontend, show group name + avatars

### Add Profile Picture
- Add `avatar: String` field to User schema
- Add a Cloudinary upload endpoint to User Service
- Update profile page with image picker

### Add Message Deletion
- Add `deleted: Boolean` to Messages schema
- Add a DELETE route to chat service
- Emit `messageDeleted` socket event
- Frontend: replace deleted message content with "This message was deleted"

### Add Push Notifications
- When receiver is offline (not in `userSocketMap`), send a push notification via Firebase Cloud Messaging (FCM) instead of/in addition to socket emit

### Add Docker Compose
- Create a single `docker-compose.yml` at root with services: user-service, chat-service, mail-service, frontend, rabbitmq, redis, mongodb
- Remove the need to run 4 terminals manually

### Switch to Separate Databases Per Service
- Give user service its own MongoDB database (`userServiceDB`)
- Give chat service its own MongoDB database (`chatServiceDB`)
- Chat service can still call User Service REST API for user data (existing pattern)

### Add Token Refresh
- Current tokens expire in 15 days
- Add a `POST /refresh` endpoint that accepts a valid expiring token and returns a new one
- Store refresh tokens in Redis

### Production Deployment
- Use environment-specific `.env.production` files
- Update `user_service` and `chat_service` URLs in `appContext.tsx` to production URLs
